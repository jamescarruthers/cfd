# Deploy the editor and optional compute API

GitHub Pages hosts the browser editor. OpenFOAM runs on a separate Linux compute API; Pages cannot run the mesher or solver. The editor uses WebGPU for 3D visualization when supported and falls back to WebGL. OpenFOAM solves on two or four CPU processes with MPI.

The repository's Pages Actions workflow builds and publishes the static editor. On Pages, enter a deployed compute URL and its API token in the connection form. The compute URL is the HTTPS origin printed by your backend deployment, without `/api`; the editor adds API paths. Browser access to a local `http://` backend from an HTTPS Pages site is subject to mixed-content restrictions, so use an HTTPS remote backend for Pages.

## Optional Modal backend

`modal_app.py` describes a four-CPU, 4 GiB backend using Node 22, Debian 13, the Debian OpenFOAM package, and this repository's existing API. No Modal deployment or account configuration is performed by installing or importing this file.

1. Install the tested SDK in a local virtual environment and authenticate your Modal account:

   ```sh
   python3 -m venv .venv
   . .venv/bin/activate
   python -m pip install 'modal==1.6.1'
   modal token new
   ```

2. In the [Modal Secrets dashboard](https://modal.com/secrets), create a Secret named `flow-compute` containing these two keys. Enter their values in Modal's secure settings:

   | Key | Value |
   | --- | --- |
   | `CFD_API_TOKEN` | A long, random token generated by your password manager; use at least 32 random bytes. |
   | `CFD_ALLOWED_ORIGINS` | Exact browser origins separated by commas, such as `https://jamescarruthers.github.io`. Do not include `/cfd/`, a trailing slash, or a wildcard. Add another origin explicitly when using a custom domain. |

   The bearer token controls access to job creation, polling, cancellation, results, and downloads. Share it only with people allowed to use the compute service. Keep tokens and Modal credentials out of source files, GitHub Pages build variables, Git commits, and URLs. The editor's connection token is provided at runtime.

3. From the repository root, when ready to create the cloud service:

   ```sh
   modal deploy deploy/modal_app.py
   ```

4. Open the deployed Pages editor, enter the HTTPS compute URL and token, and connect. The authenticated health check should report OpenFOAM ready. Start with a small scene and inspect mesh quality, residual history, and convergence before increasing resolution.

The image copies only package manifests, backend sources, and required geometry-validation sources. Dependency installation uses `npm ci --omit=dev`. OpenFOAM is installed through Debian's signed package repositories. Authentication and explicit allowed browser origins are mandatory before the public API starts.

## Costs, files, and restarts

This deployment keeps one container warm and limits the API to one container. This preserves the current in-memory queue across individual HTTP requests and keeps background solver processes alive, but it incurs warm-container costs even when idle. Stop the app in Modal when it is not needed. Increasing CPU count also requires adjusting the supported solver settings.

By default, cases are stored in the `flow-studio-cases` Modal Volume under `/data/jobs` and committed approximately every 30 seconds. Download useful cases from the editor. Volume storage incurs its own costs; remove old cases through Modal's volume controls when no longer needed. A container restart interrupts active solves and clears the API's in-memory job registry. Retained case files do not currently restore jobs or make their old IDs available through the API. The last uncommitted files may be lost if a container stops abruptly.

For temporary case files without a Volume, set the following before deploying:

```sh
CFD_MODAL_PERSIST_CASES=0 modal deploy deploy/modal_app.py
```

This version serves one trusted group using a shared token. It has no user accounts, per-user job isolation, resumable jobs, billing limits, or distributed queue. Job submission is bounded, and the server validates geometry and simulation settings. A public multi-user product needs those additional controls before broader access.

## What the results establish

The compute path uses a real 3D OpenFOAM finite-volume solver with SI inputs and physical velocity and pressure outputs. Established numerics support engineering workflows, but this application's integration is not independently certified. Engineering decisions still require suitable boundary conditions and turbulence models, mesh independence, convergence, and comparison with trusted benchmarks or measurements.

The current flow setup uses a uniform inlet on the computational domain's upstream face. The editor's air emitter controls that inlet; independently positioned volumetric sources and calibrated fan or nozzle models are future capabilities. The Debian v1912 build runs without function objects and exports fields through `foamToVTK` because its function-object dictionary hashing fails in this runtime.
